# CLAUDE.md — Polygon problem-prep orchestrator

## Что это за репозиторий

Python-оркестратор, который берёт структурированный спек задачи
(`specs/<problem_id>.yaml`, формат — см. `docs/SPEC_FORMAT.md`) и прогоняет
его через последовательность **генеративных шагов**. Каждый шаг — отдельный
вызов LLM по API (не через Claude Code) плюс минимальная механическая
проверка результата. Результат — черновики артефактов Polygon-задачи
(`.tex`-условие, ограничения/группы тестов, генераторы + FreeMarker-скрипт,
опционально — черновики решений), которые автор потом сам проверяет и
докручивает руками в Polygon.

**Claude Code не генерирует содержимое задач.** Роль Claude Code —
писать/поддерживать код самого оркестратора, промпт-шаблоны, парсеры спека,
раннер compile-check/timeout. Контент задач производит отдельная модель,
вызываемая оркестратором через API.

## Скоуп (текущий)

В скоупе:
- черновик условия в LaTeX;
- выбор ограничений (N/TL/ML, тестовые группы) — **только на основе
  асимптотики, явно данной автором в спеке**, без самостоятельного вывода
  сложности из текста легенды;
- генераторы (C++/testlib) и FreeMarker test-script;
- опциональные черновики авторских решений (ok/wa/tle) для последующей
  ручной проверки автором.

Вне скоупа (сознательно, добавим отдельно позже):
- полноценный судящий контур (различение TLE/MLE/RE, батч-стресс-тестинг,
  сравнение решений между собой на реальных лимитах);
- интеграция с Polygon API (загрузка файлов, commit, packages).

Минимальная страховка вместо судящего контура на этом этапе:
- **compile-check** после каждого сгенерированного C++-файла
  (валидатор/чекер/генератор/решение) — компилируется или нет, без запуска;
- **timeout-обёртка** вокруг любого запуска сгенерированного бинаря
  (например, прогон генератора для смоук-теста) — просто убить процесс по
  таймауту, без анализа TLE/MLE отдельно.

## Роль каждого генеративного шага

1. **`statement_draft`** — вход: секция `statement_draft` спека. Выход:
   черновик `.tex` условия (легенда/ввод/вывод/примечание к примерам),
   следующий структуре и стилистическим правилам из
   `templates/tutorials/requirements.md` (раздел "Условие задачи").
2. **`constraints_pick`** — вход: секция `constraints` спека, в первую
   очередь `intended_complexity` и `complexity_reasoning`. Выход:
   зафиксированные диапазоны переменных, TL/ML, разбиение на тестовые
   группы — согласовано с asymптотикой, которую дал автор. Модель **не
   имеет права** сама придумывать асимптотику по легенде — если
   `intended_complexity` пуст, шаг обязан завершиться ошибкой
   "недостаточно данных", а не угадывать.
3. **`generators_and_script`** — вход: секция `generation` спека +
   зафиксированные ограничения из шага 2. Выход: C++/testlib-генераторы (на
   основе `templates/gen_rand.cpp` и т.п., см. `base_template_refs`) и
   FreeMarker test-script (`flat` или `groups`-стиль — см.
   `templates/test_script` vs `templates/test_script_groups`).
4. **`solutions_draft`** — вход: секция `solutions` спека + зафиксированные
   ограничения. Выход: черновики решений с заявленными вердиктами
   (ok/wa/tl), которые автор обязательно перепроверяет и вероятно
   переписывает сам — это не финальные решения.

Каждый шаг — чистая функция от (спек + результаты предыдущих шагов) к
артефакту(-ам) + отчёту о неуверенности. Шаги идемпотентны: повторный запуск
с тем же входом должен быть безопасен (перезаписывает `outputs/<id>/...`, не
аккумулирует состояние).

## Правило эскалации при неуверенности

Это правило применяется к промптам всех четырёх шагов (см. `prompts/*/system.md`):

- Если для ответа не хватает данных, явно заданных автором в спеке (в первую
  очередь — asymптотика, точность вещественного ответа, поведение на
  граничных случаях, которые не описаны в `special_guarantees`) — модель
  обязана **не додумывать**, а вернуть структурированный ответ с полем
  `uncertain: true` и конкретным указанием, какого именно поля спека не
  хватает.
- Если данных достаточно, но решение неоднозначно (например, автор не
  указал верхнюю границу переменной, `max: null`) — модель может предложить
  вариант, но обязана явно пометить его как `status: proposed` (не
  `status: confirmed`), и указать, на основании чего сделано предположение.
- Ссылки на источники за пределами приложенных `tutorials/*.md` (например,
  на testlib-документацию) допустимы, но должны быть явными URL, а не
  пересказом "по памяти".
- Оркестратор (Python-код) должен различать эти два случая механически:
  ответ с `uncertain: true` останавливает пайплайн для этого problem_id и
  требует правки спека; ответ с `status: proposed` полях — не останавливает
  пайплайн, но помечает соответствующие файлы/поля в `outputs/` как
  требующие ручной проверки автором (например, суффиксом `# PROPOSED,
  REVIEW ME` в сгенерированном файле или отдельным полем в
  `constraints.yaml`).

## Маршрутизация моделей по критичности шага

Критичные по содержанию шаги (там, где ошибка стоит дороже — неверная
асимптотика, неверные ограничения, некорректное решение) идут через более
сильную модель; механические/боилерплейт-шаги — через более быструю/дешёвую.

| Шаг                        | Критичность | Предлагаемый класс модели |
|-----------------------------|-------------|----------------------------|
| `constraints_pick`          | высокая     | сильная модель             |
| `solutions_draft`           | высокая     | сильная модель             |
| `statement_draft` (LaTeX)   | средняя     | сильная или средняя — решить по бюджету |
| `generators_and_script`     | низкая/механическая | быстрая модель      |

Конкретные имена моделей и параметры (temperature, max_tokens) — в
`orchestrator/model_router.py`, не в промптах; промпты не должны зависеть от
того, какая именно модель их выполняет.

## Как использовать приложенные материалы

- `templates/tutorials/requirements.md`, `templates/tutorials/polygon.md`,
  `templates/tutorials/freemarker.md` — это **правила**, а не справочный
  материал "для общего развития". Промпты должны явно инструктировать
  модель следовать им как обязательным ограничениям, а не как совету.
- `templates/problem_lib.h`, `templates/validator*.cpp`,
  `templates/checker.cpp`, `templates/gen_rand.cpp`, `templates/test_script*`
  — это основа, которую нужно расширять, а не переизобретать. Если шаг
  генерации создаёт новый генератор — он должен `#include "problem_lib.h"` и
  следовать тем же соглашениям об именовании (`register...`, `opt<T>(...)`,
  стиль `gen_test` из `gen_rand.cpp`).

## Не в скоупе этого CLAUDE.md

- Как именно вызывается Polygon API — будет отдельный документ, когда дойдём
  до интеграции.
- Полный судящий контур (TLE/MLE различение, стресс-тесты на паре решений) —
  отдельная будущая задача, здесь не проектируется.
