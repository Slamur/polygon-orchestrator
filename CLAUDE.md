# CLAUDE.md — Polygon problem-prep orchestrator

## Что это за репозиторий

Python-оркестратор, который берёт структурированный спек задачи
(`problems/<problem_id>/spec.yaml`, формат — см. `docs/SPEC_FORMAT.md`) и прогоняет
его через последовательность **генеративных шагов**. Каждый шаг — отдельный
вызов LLM по API (не через Claude Code) плюс минимальная механическая
проверка результата. Результат — черновики артефактов Polygon-задачи
(`.tex`-условие, ограничения/группы тестов, генераторы + FreeMarker-скрипт,
опционально — черновики решений), которые автор потом сам проверяет и
докручивает руками в Polygon.

**Claude Code не генерирует содержимое задач.** Роль Claude Code —
писать/поддерживать код самого оркестратора, промпт-шаблоны, парсеры спека,
раннер compile-check/timeout. Контент задач производит отдельная модель,
вызываемая оркестратором через API.

## Скоуп (текущий)

В скоупе:
- черновик условия в LaTeX;
- выбор ограничений (N/TL/ML, тестовые группы) — **только на основе
  асимптотики, явно данной автором в спеке**, без самостоятельного вывода
  сложности из текста легенды;
- генераторы (C++/testlib) и FreeMarker test-script;
- опциональные черновики авторских решений (ok/wa/tle) для последующей
  ручной проверки автором;
- опциональный черновик кастомного чекера (C++/testlib, по паттерну
  read_and_check — см. `checker.cpp` учебной задачи в `examples/`), только если
  `checker.custom_needed: true` в спеке; если используется стандартный
  чекер (`checker.standard`) — этот шаг не запускается, генерировать
  нечего;
- создание задачи на Polygon по `problem_id` из спека через Polygon API
  (`orchestrator/polygon/`; привязка `problem_id` -> Polygon problemId
  хранится в `problems/<problem_id>/polygon_state.json`) и перенос TL/ML из
  `problems/<problem_id>/constraints.yaml` через `problem.updateInfo`
  (`set_constraints`), загрузка `problems/<problem_id>/problem_lib.h` как
  resource-файла (`upload_problem_lib`), загрузка
  `problems/<problem_id>/validator.cpp` и назначение его валидатором
  (`upload_validator`), назначение чекера (`upload_checker`: для
  `checker.custom_needed: true` — загрузка `problems/<problem_id>/checker.cpp`,
  иначе — стандартный чекер из `checker.standard` без загрузки файла).
  Шаги загружают только то, что изменилось с последней синхронизации с
  Polygon (база — `revision`/`synced` в `polygon_state.json`, см.
  `orchestrator/polygon/sync.py`). После каждого polygon-шага, который
  что-то загрузил (кроме `create_problem`), рабочая копия задачи
  коммитится (`problem.commitChanges`, `minorChanges=true`) — при падении
  на очередном шаге всё сделанное предыдущими уже в ревизии.
  Остальные шаги интеграции (прочие файлы, packages) — позже, по мере
  проработки.

Вне скоупа (сознательно, добавим отдельно позже):
- полноценный судящий контур (различение TLE/MLE/RE, батч-стресс-тестинг,
  сравнение решений между собой на реальных лимитах).

Минимальная страховка вместо судящего контура на этом этапе:
- **compile-check** после каждого сгенерированного C++-файла
  (валидатор/чекер/генератор/решение) — компилируется или нет, без запуска;
- **timeout-обёртка** вокруг любого запуска сгенерированного бинаря
  (например, прогон генератора для смоук-теста) — просто убить процесс по
  таймауту, без анализа TLE/MLE отдельно.

## Роль каждого генеративного шага

1. **`statement_draft`** — вход: секция `statement_draft` спека. Выход:
   черновик условия в `problems/<id>/statement/` — отдельные `.tex` на
   легенду/ввод/вывод/примечание + input каждого примера в
   `examples/example_<N>.txt` (набор имён проверяется до записи на диск),
   следующий структуре и стилистическим правилам из
   `templates/tutorials/statement.md`.
2. **`constraints_pick`** — вход: секция `constraints` спека, в первую
   очередь `intended_complexity` и `complexity_reasoning`, + формат ввода из
   `statement_draft` (`formal_input_sketch`, `indexing`, input примеров —
   источник порядка чтения для валидатора; легенда не передаётся). Выход:
   зафиксированные диапазоны переменных, TL/ML, разбиение на тестовые
   группы (в `constraints.yaml`, включая секцию `validator` —
   `constants`/`checks`, описывающую, что именно должен проверять
   валидатор, по формату `templates/constraints_format.yaml`) +
   `validator.cpp` (по образцу `validator.cpp` из референсов, если есть),
   реализующий 1-в-1 `validator.constants`/`validator.checks`, которые шаг
   сам же и зафиксировал в `constraints.yaml` — никаких проверок сверх или
   помимо перечисленных там. Генерация `validator.cpp` — не отдельный шаг,
   а последний под-шаг того же рассуждения об ограничениях в рамках одного
   вызова модели: валидатор целиком выводится из решений, которые
   `constraints_pick` и так принимает, и раздельные шаги/вызовы рисковали бы
   разойтись между `constraints.yaml` и `validator.cpp`. Модель **не имеет
   права** сама придумывать асимптотику по легенде — если
   `intended_complexity` пуст, шаг обязан завершиться ошибкой
   "недостаточно данных", а не угадывать; в этом случае `validator.cpp`
   тоже не пишется — весь ответ шага уходит в `uncertain` целиком.
3. **`generators_and_script`** — вход: секция `generation` спека +
   формат ввода из `statement_draft` (`formal_input_sketch`, `indexing`,
   input примеров — отдельного поля `generation.input_shape` в спеке нет,
   чтобы не дублировать описание формата входа) +
   зафиксированные ограничения из шага 2 + (если секция `solutions` в
   спеке задана) `solutions.known_wrong_approaches`. Выход: C++/testlib-
   генераторы (на основе `generators/*.cpp` из референсов спека) и
   FreeMarker test-script (`flat`-стиль — по образцу `test_script` из
   референсов; если образца `test_script_groups` нет, скрипт
   `test_script_groups` строится на той же структуре с разбивкой тестов по
   группам и помечается `proposed`). Внутри шаг делает две разные по
   характеру вещи, и это важно не смешивать: если `generation.generator_ideas`
   уже описывает нужный генератор — это механическая реализация; для каждого
   пункта `known_wrong_approaches`, под который в спеке ещё нет готового
   генератора, шаг обязан сам придумать тест/генератор, целенаправленно
   проверяющий именно этот сценарий, и вернуть его с `status: proposed` +
   обоснованием в `notes` (почему этот тест ловит именно такую ошибку) —
   как и с любым другим предположением модели, это не самостоятельное
   решение, а предложение для проверки автором. Если ни `generator_ideas`,
   ни `known_wrong_approaches` не дают зацепок для стресс-тестов — шаг не
   должен молчать об этом: явно указать в `notes`, что adversarial-случаи
   не придуманы и нужна ручная проверка.
4. **`solutions_draft`** — вход: секция `solutions` спека +
   `constraints.intended_complexity` + полный текст `constraints.yaml` из
   шага 2 + условие из `statement_draft` в части ввода-вывода
   (`formal_input_sketch`, `formal_output_sketch`, `indexing`, примеры с
   ответами, `legend_sketch` — для понимания терминов `algorithm_hint`, не
   как источник алгоритма). Выход: черновики решений с заявленными вердиктами
   (ok/wa/tl/tl_ok), которые автор обязательно перепроверяет и вероятно
   переписывает сам — это не финальные решения.
5. **`checker_draft`** (опциональный, как и `solutions_draft`) — запускается,
   только если `checker.custom_needed: true` в спеке; если используется
   стандартный чекер (`checker.standard`, например `ncmp`) — шаг не
   запускается вообще, генерировать нечего. Вход: `checker.custom_comparison_notes`
   (самодостаточное текстовое описание формата ответа и правила сравнения —
   автор пишет его сам, шаг ничего не выводит из условия/легенды
   самостоятельно). Выход: `checker.cpp` по паттерну read_and_check (как в
   `checker.cpp` учебной задачи `array--prefix-sums`) — функция `read_answer(InStream&)`,
   параметризуемая потоком (используется для `ans` и `ouf` одинаково),
   которая читает И валидирует ответ, оборачивается в `read_answer_from`
   с проверкой `seekEof()` (лишние данные после ответа → `_pe`). Модель
   реализует ровно то сравнение, которое описано в
   `custom_comparison_notes` — если оно неполно (например, не указано,
   чувствительно ли сравнение к регистру, или что делать с пустым вводом),
   шаг обязан вернуть `status: uncertain`, а не домысливать поведение
   чекера — ошибка здесь особенно дорога: чекер, который слишком мягко или
   слишком строго сравнивает ответы, может пропустить неверное решение или
   забраковать верное.

Каждый шаг — чистая функция от (спек + результаты предыдущих шагов) к
артефакту(-ам) + отчёту о неуверенности. Шаги идемпотентны: повторный запуск
с тем же входом должен быть безопасен (перезаписывает `problems/<id>/...`, не
аккумулирует состояние) — но по умолчанию повторный запуск с **тем же**
входом не должен даже дойти до вызова модели, см. ниже "Кэширование по хешу
спека".

## Запуск

Задачи в этом проекте независимы друг от друга и адресуются по
`problem_id`: всё, что относится к задаче, — спек и результаты шагов —
лежит в её каталоге `problems/<problem_id>/` (спек — `spec.yaml`).
Обычно работа идёт над одной задачей, поэтому `problem_id` в CLI стоит
первым, а команда к нему — после: `orchestrator [--problems-dir ...]
<problem_id> <init|llm|polygon> [команда] [флаги]`. Пакетного прогона по всем
спекам (`--all`) сейчас нет — убран как ненужный, вернуть при
необходимости. То, что должно обеспечить CLI (`orchestrator/cli.py` —
парсер, `orchestrator/cli_commands.py` — сами команды):

- `orchestrator <problem_id> init` — создаёт каталог `problems/<problem_id>/`
  (если его нет) с черновиком `spec.yaml` из
  `templates/spec_template.yaml`: `problem_id` подставлен, остальные
  поля пустые, с комментариями-подсказками. Существующий `spec.yaml` не
  перезаписывается. Ни модель, ни Polygon не вызывает.
- `orchestrator <problem_id> llm generate [--step NAME] [--force]` — прогон
  задачи (всех шагов или одного конкретного); шаги, для которых кэш
  валиден, пропускаются автоматически (см. ниже). `--force` игнорирует кэш
  и вызывает модель заново.
- `orchestrator <problem_id> llm status` — без вызовов модели: печатает
  таблицу "шаг → cache hit / stale / not run", используя те же хеши, что и
  `llm generate`. Полезно, чтобы до реального запуска увидеть, что вообще
  изменилось после правки спека.
  У `stale` указано, что именно изменилось (поле спека, upstream-артефакт,
  промпт или приложенный документ, модель) — по хешам частей входа,
  которые кэш хранит рядом с общими хешами.
- `orchestrator <problem_id> llm accept [--step NAME]` — без вызовов
  модели: принимает текущие артефакты `stale`-шагов как актуальные
  (перезаписывает их кэш текущими хешами, `accepted: true`). Для случаев,
  когда изменилось то, что не должно менять результат (рефакторинг
  промптов/шаблонов), или автор уже поправил файлы руками и подогнал под них
  спек. Шаги `not run`, `uncertain` и без артефакта на диске не принимаются.
- `orchestrator <problem_id> polygon push [--step NAME] [--force]` — прогон
  polygon-шагов по порядку `POLYGON_STEP_ORDER`; каждый шаг загружает
  только элементы задачи, изменившиеся с последней синхронизации (как
  `git push` с проверкой fast-forward). Перед первой загрузкой один запрос
  сверяет ревизию задачи на Polygon с записанной: если Polygon меняли в
  обход оркестратора (другая ревизия или незакоммиченные правки в рабочей
  копии) — push останавливается и предлагает `polygon pull` или
  `--force`. Ревизия неизвестна (задача привязана к уже существующей на
  Polygon или до появления этой проверки) — push тоже останавливается до
  `polygon pull`; у задачи, только что созданной `create_problem`, ревизия
  записывается сразу. `--force` загружает всё без проверки ревизии и
  затирает закоммиченные правки, сделанные на Polygon (они остаются в
  истории ревизий). Незакоммиченные правки в рабочей копии на Polygon
  останавливают push всегда, даже с `--force`: коммит после шага унёс бы
  их в ревизию оркестратора. Реально обращается к Polygon
  API — те же ограничения на запуск без явной команды, что и для
  `llm generate`.
- `orchestrator <problem_id> polygon status` — что из polygon-шагов уже
  сделано, без обращения к сети: `done / stale / not run` по
  `PolygonStep.compute_status` (сравнение локальных файлов с базой
  синхронизации — тем, что последний push загрузил или pull увидел на
  Polygon). Правки на Polygon после последней синхронизации отсюда не
  видны — их замечает только `polygon push`/`pull`.

- `orchestrator <problem_id> polygon pull [--polygon-id N] [--overwrite]` —
  обратное направление: привязывает `problem_id` к уже существующей на
  Polygon задаче (по `polygon_state.json`, иначе поиском неудалённой задачи
  с именем `problem_id`; `--polygon-id` дополнительно сужает поиск, если
  задач с таким именем несколько), сравнивает с ней части задачи, которыми
  пользуется оркестратор (условие и примеры, TL/ML, валидатор,
  нестандартный чекер, генераторы, test-script, решения), скачивает в
  `problems/<problem_id>/` недостающие локально и переписывает базу
  синхронизации по текущей ревизии Polygon. Отличающиеся от Polygon файлы
  без `--overwrite` остаются локальными (следующий push их загрузит), с
  `--overwrite` заменяются версией с Polygon, а старые переносятся в
  `.pull_backup/` (как `git fetch` / `git reset --hard`). Файлы, которых
  нет на Polygon, явно перечисляются и никогда не удаляются;
  `constraints.yaml` — результат `constraints_pick` — не перезаписывается
  и с `--overwrite` (TL/ML — только сообщение о расхождении). Отказывается
  работать, если на Polygon есть незакоммиченные правки. Каталог задачи
  создаётся, если его нет; спек не нужен. На Polygon ничего не меняет
  (только чтение), но в сеть ходит — те же ограничения на запуск без явной
  команды. Детали — в докстринге `orchestrator/polygon/pull.py`.

`problem_id` дополняется по Tab (`argcomplete`; разовая настройка shell — в
`docs/SETUP.md`): кандидаты — каталоги задач в `problems/`, со спеком или
без (`polygon status|pull` спек не нужен, а команда на момент дополнения
`problem_id` ещё не набрана); читаются при каждом нажатии, ничего не
кэшируется. На каждый Tab shell запускает `cli.py`
целиком, поэтому на верхнем уровне `cli.py` нельзя импортировать пайплайны
(pydantic, requests) — они подгружаются лениво через `cli_commands.py`.
Дополнение только подсказывает: в команду уходит полное имя задачи,
сокращённые имена CLI не принимает.

Группировку задач в контесты/раунды с общими дефолтами (TL/ML-конвенции,
общий стиль тестовых групп на весь раунд) в спек пока сознательно не
закладываем — решения по этому вопросу пока нет. Если понадобится, самое
дешёвое расширение — необязательное поле `extends: <contest_id>.yaml` в
спеке, значения которого мёрджатся в спек как дефолты перед валидацией; сам
`SPEC_FORMAT.md` под это не переписан, чтобы не фиксировать формат раньше
времени.

## Кэширование по хешу спека

Каждый вызов генеративной модели стоит денег и времени, а спеки будут
правиться итеративно (черновик → правки → повторный прогон). Поэтому
шаг не должен вызывать модель повторно, если ничего из того, что на него
влияет, не изменилось с прошлого успешного запуска.

Что входит в хеш для шага (считается в `orchestrator/cache.py`,
используется в `orchestrator/pipeline.py` перед вызовом
`model_router`):

- каноническое JSON-представление той секции спека, от которой зависит шаг
  (`statement_draft` → секция `statement_draft`; `constraints_pick` →
  секция `constraints` + формат ввода из `statement_draft`
  (`formal_input_sketch`, `indexing`, input примеров — правка формата входа
  должна инвалидировать и `validator.cpp`); `generators_and_script` → секция
  `generation` + тот же формат ввода из `statement_draft` (правка
  формата входа в условии должна инвалидировать кэш генераторов, даже если
  секция `generation` не менялась) +
  содержимое `problems/<id>/constraints.yaml`, полученное на шаге 2, +
  `solutions.known_wrong_approaches` (если секция `solutions` задана —
  правка `known_wrong_approaches` тоже должна инвалидировать кэш этого
  шага, не только правка `generation`); `solutions_draft` → секция
  `solutions` + `constraints.intended_complexity` + ввод-вывод из
  `statement_draft` (формат ввода и вывода, `indexing`, примеры с ответами,
  легенда) + `constraints.yaml`). Сборка этой части `statement_draft` —
  `statement_io_section` в `orchestrator/steps/base.py`, общая для всех
  трёх шагов;
- хеш содержимого промпт-шаблонов этого шага (`prompts/<step>/system.md` +
  `user.md.j2`) и приложенных к нему документов (`templates/` и
  файлы референсов спека) — если промпт или образец поправили, кэш должен
  инвалидироваться, даже если спек не менялся;
- имя/версия модели из `model_router.py` для этого шага (смена модели тоже
  инвалидирует кэш).

Логика в `pipeline.py` перед каждым шагом:

1. Посчитать `input_hash` по правилам выше.
2. Прочитать `problems/<id>/.cache/<step>.json`, если есть.
3. Если `input_hash` совпадает с сохранённым **и** ожидаемые файлы
   артефактов на месте **и** сохранённый `status` не был `uncertain`
   (кэшировать "провал по недостатку данных" бессмысленно — он должен
   всплывать при каждом запуске, пока спек не поправят) — шаг пропускается,
   в лог идёт "cache hit", `problems/` не трогается.
4. Иначе — обычный вызов модели, и по успешному результату файл кэша
   перезаписывается новым `input_hash`/`prompt_hash`/`model`/`status`/
   `timestamp`.

Помимо общих `input_hash`/`prompt_hash`, кэш хранит хеши по частям
(`input_parts`: поля секции спека и upstream-артефакты; `prompt_parts`:
промпт-шаблоны и каждый приложенный документ) — решение о cache hit они не
меняют, только объясняют в `llm status`/`llm generate`, что изменилось.
`orchestrator <id> llm accept` записывает текущие хеши без вызова модели (см.
"Запуск").

`--force` в CLI полностью обходит этот механизм для явной принудительной
перегенерации.

## Правило эскалации при неуверенности

Это правило применяется к промптам всех четырёх шагов (см. `prompts/*/system.md`):

- Если для ответа не хватает данных, явно заданных автором в спеке (в первую
  очередь — asymптотика, точность вещественного ответа, поведение на
  граничных случаях, которые не описаны в `special_guarantees`) — модель
  обязана **не додумывать**, а вернуть структурированный ответ с полем
  `uncertain: true` и конкретным указанием, какого именно поля спека не
  хватает.
- Если данных достаточно, но решение неоднозначно (например, автор не
  указал верхнюю границу переменной, `max: null`) — модель может предложить
  вариант, но обязана явно пометить его как `status: proposed` (не
  `status: confirmed`), и указать, на основании чего сделано предположение.
- Ссылки на источники за пределами приложенных `tutorials/*.md` (например,
  на testlib-документацию) допустимы, но должны быть явными URL, а не
  пересказом "по памяти".
- Оркестратор (Python-код) должен различать эти два случая механически:
  ответ с `uncertain: true` останавливает пайплайн для этого problem_id и
  требует правки спека; ответ с `status: proposed` полях — не останавливает
  пайплайн, но помечает соответствующие файлы/поля в `problems/` как
  требующие ручной проверки автором (например, суффиксом `# PROPOSED,
  REVIEW ME` в сгенерированном файле или отдельным полем в
  `constraints.yaml`).

## Маршрутизация моделей по критичности шага

Критичные по содержанию шаги (там, где ошибка стоит дороже — неверная
асимптотика, неверные ограничения, некорректное решение) идут через более
сильную модель; механические/боилерплейт-шаги — через более быструю/дешёвую.

| Шаг                        | Критичность | Предлагаемый класс модели |
|-----------------------------|-------------|----------------------------|
| `constraints_pick`          | высокая     | сильная модель             |
| `solutions_draft`           | высокая     | сильная модель             |
| `checker_draft`              | высокая (при неполном `custom_comparison_notes`) | средняя модель |
| `statement_draft` (LaTeX)   | средняя     | средняя модель              |
| `generators_and_script`     | средняя     | средняя модель             |

`checker_draft` формально механический, когда `custom_comparison_notes`
полон и однозначен (перевод текстового описания в код по паттерну
read_and_check) — но ошибка здесь дороже, чем в среднем механическом шаге:
неверно реализованное сравнение может молча пропускать неверные решения или
браковать верные, и это может остаться незамеченным долго. Средняя модель —
компромисс: если на практике `custom_comparison_notes` часто оказывается
недостаточно точным и шаг слишком часто уходит в `uncertain`
(что само по себе не страшно — так и задумано), можно поднять шаг до сильной
модели, как `constraints_pick`/`solutions_draft`.

`generators_and_script` изначально был помечен как чисто механический —
это оказалось неточно. Реализация генератора по уже готовой идее (из
`generation.generator_ideas`) действительно механическая, но
**придумывание** хитрых/adversarial тестов — самостоятельное рассуждение
о том, как сломать конкретный неверный алгоритм, — не менее содержательная
задача, чем `constraints_pick`. Явный источник для такого рассуждения —
`solutions.known_wrong_approaches` (см. "Роль каждого генеративного шага",
п.3, обновлено). Поэтому шаг поднят до "средняя модель": реализация
шаблонного генератора не требует Opus-уровня, но для содержательного
дизайна стресс-тестов быстрой модели может не хватать — если на практике
качество предложенных тестов будет слабым, следующий шаг эскалации — до
сильной модели, как у `constraints_pick`/`solutions_draft`.

Классы моделей ("strong-model"/"medium-model"/"fast-model") и `effort` на
шаг живут в `orchestrator/model_router.py` — этот модуль вендоронезависим,
он не знает конкретных имён моделей. Соответствие класса конкретной модели
вендора (например, `"strong-model" -> "claude-opus-5"`), авторизация, retry
и формат структурированного вывода — всё это инкапсулировано в реализации
`LLMClient` (`orchestrator/llm_client.py`), по умолчанию `ClaudeCodeClient`
(`orchestrator/llm_clients/claude_code_client.py`: модели через Claude Code
CLI, расход из лимитов подписки, а не с API-баланса — см.
`docs/SETUP.md`); при `ORCHESTRATOR_LLM_BACKEND=anthropic-api` —
`AnthropicClient` (`orchestrator/llm_clients/anthropic_client.py`, те же
модели через Anthropic API). Промпты не должны
зависеть от того, какая именно модель/вендор их выполняет — вся эта
информация не должна течь в `prompts/`.

## Как использовать приложенные материалы

- `templates/tutorials/*.md` (кроме `polygon.md`) — это **правила**, а не справочный
  материал "для общего развития". Промпты должны явно инструктировать
  модель следовать им как обязательным ограничениям, а не как совету.
  Правила разбиты по темам, и шаг получает только нужные ему
  (`STEP_CONTEXT_DOCUMENTS`), поэтому правка одной темы инвалидирует кэш
  только читающих её шагов. Файлы пишутся для модели: каждый
  самодостаточен, без ссылок на другие файлы правил. `polygon.md` — справка
  по интерфейсу Polygon, ни одному шагу не прикладывается.
- `templates/problem_lib.h` и файлы учебных задач
  `examples/<problem_id>/` (`validator.cpp`, `checker.cpp`,
  `generators/*.cpp`, `test_script`, `solutions/*`)
  — это основа, которую нужно расширять, а не переизобретать. Если шаг
  генерации создаёт новый генератор — он должен `#include "problem_lib.h"` и
  следовать тем же соглашениям об именовании (`register...`, `opt<T>(...)`,
  стиль `gen_test` из `generators/*.cpp`). У каждой задачи своя копия
  `problem_lib.h` (`problems/<problem_id>/problem_lib.h`, см.
  `PROBLEM_LIB_FILENAME` в `orchestrator/steps/base.py`): шаблон — только её
  начальное содержимое, правка шаблона в уже существующие копии не
  попадает. Compile-check ищет `problem_lib.h` сначала в каталоге задачи,
  потом в `templates/`; модели прикладывается шаблон.
- `templates/` — общее для всех задач и прикладывается к шагам
  всегда (`STEP_CONTEXT_DOCUMENTS` в `orchestrator/steps/base.py`); там же
  `constraints_format.yaml` — формат результата `constraints_pick`, который
  читают следующие шаги и `polygon push`. `examples/` — учебные
  задачи, по каталогу `<вид входных данных>--<суть задачи>` на каждую
  (`array--prefix-sums`), в раскладке `problems/<problem_id>/` плюс свой
  спек `spec.yaml` (`problem_id` = имя каталога; ожидаемый по нему
  результат `constraints_pick` — `constraints.yaml` рядом; при правке
  образцов держать оба согласованными с ними и с `constraints_format.yaml`
  — это проверяет `tests/test_example_templates.py`, там же compile-check
  всех `.cpp` образцов).
- Образцы (файлы других задач) прикладываются к вызову модели только как
  **референсы спека** — поле `references` в корне спека (для всех шагов) и
  в секциях шагов (только для своего шага), см. `docs/SPEC_FORMAT.md`,
  "Референсы", и `orchestrator/references.py`. Референс — файл или каталог
  в раскладке `problems/<problem_id>/` (учебная задача из
  `examples/`, прошлая задача автора в `problems/`); каждый шаг
  берёт из каталога только свою часть (`REFERENCE_DOCUMENTS`), решения —
  только на языках из `solutions.languages`. Без референсов шаг получает
  только `templates/`. Содержимое референсов входит в хеш промпта
  шага (см. "Кэширование по хешу спека"), сами пути `references` в
  `input_hash` не входят. Промпты обязаны явно
  разделять, что из образца переносить (каркас файла, ввод-вывод, функции
  testlib, композицию генераторов через конвейер), а что нет (формат данных,
  имена переменных и логику задачи-образца), и работать без образцов — см.
  `docs/PROMPTS.md`, "Приложенные шаблоны как образцы".

## Git-workflow для разработки оркестратора

`main` — стабильная ветка. Прямые коммиты в `main` не делаются, в том числе
Claude Code — весь код оркестратора (парсер спека, шаги, кэш, CLI, промпты)
проходит через ветку и PR, даже если ревьюер один (автор).

Правила для Claude Code:

1. **Никогда не коммитить напрямую в `main`.** Перед началом любой работы —
   создать ветку от актуального `main`: `git checkout main && git pull &&
   git checkout -b <branch>`.
2. **Именование веток**: `feature/<кратко-что-делаем>` для нового
   функционала, `fix/<кратко>` для багфиксов, `chore/<кратко>` для
   рутины (обновление зависимостей, форматирование). Один логический кусок
   работы — одна ветка (например, `feature/spec-validation`,
   `feature/cache-by-hash`, `fix/generators-compile-check`), не смешивать
   несвязанные изменения в одной ветке/PR.
3. **Коммиты** — в стиле Conventional Commits (`feat: ...`, `fix: ...`,
   `docs: ...`, `refactor: ...`, `chore: ...`), атомарные: один коммит —
   одно осмысленное изменение, а не "накопил всё и закоммитил одним куском".
4. **По завершении работы над веткой** — запушить и открыть PR через `gh`:
   `gh pr create --fill` (или с явным summary через `--body`). Заголовок и
   описание PR должны отражать, что и зачем изменено, а не только "what" —
   в духе того, как это описано в `docs/PROMPTS.md`-контракте (явно,
   по делу, без домысливания). Ни в названии ветки, ни в коммитах, ни в
   PR не должно быть `problem_id` и деталей спеков — см. "Конфиденциальность
   problems/" ниже.
5. **Claude Code не мержит PR сам**, если это явно не попросили. Дефолт —
   PR остаётся открытым и ждёт ревью автора; merge/squash — руками через
   GitHub (или по явной команде "смержи PR").
6. Если задача явно мелкая и разовая (например, поправить опечатку в
   `docs/`) — всё равно через ветку+PR, отдельного "быстрого пути" в обход
   этого правила нет, чтобы не размывать конвенцию.

Предполагается, что `gh` CLI уже установлен и авторизован
(`gh auth login`) — без этого шаг 4 не сработает, и придётся пушить ветку и
открывать PR руками через веб-интерфейс.

Также предполагается, что в клоне выполнено `git config core.hooksPath
githooks` (см. `docs/SETUP.md`) — `githooks/pre-push` блокирует push, если
имя ветки или сообщения коммитов содержат `problem_id` — имя любого каталога в `problems/`.
Хук — страховка, а не замена правилам из раздела ниже.

## Конфиденциальность problems/

`problems/` (вместе со спеками задач `problems/<problem_id>/spec.yaml`) — в
`.gitignore` намеренно: репозиторий
оркестратора публичный, а сами задачи — нет, пока не опубликованы на
контесте. Это единственный барьер между "черновик задачи" и "виден кому
угодно с доступом к репозиторию".

Но коммиты, сообщения коммитов, названия веток, заголовок и описание PR,
код-комментарии — публичны точно так же, как и остальной код, НЕЗАВИСИМО
от .gitignore. Если название задачи или её детали попадут в любой из этих
текстов — .gitignore ничего не спасёт, утечка уже произошла.

СТРОГО ЗАПРЕЩЕНО в commit message, названии ветки, заголовке/описании PR,
код-комментариях и любых других файлах, которые коммитятся в git:
- `problem_id` конкретной задачи, над которой сейчас идёт работа;
- содержимое любых полей спека (`legend_sketch`, `formal_input_sketch`,
  `algorithm_hint` и т.д.) — включая пересказ своими словами, а не только
  дословные цитаты;
- любые другие детали, по которым можно догадаться о теме/сюжете/идее
  задачи (даже отдалённые намёки).

Это же касается тестов и их фикстур (`tests/`): в них используются только
синтетические `problem_id` (`example-problem`, `my-task`) и синтетические
спеки, а не копии или выжимки реальных файлов из `problems/`.

Названия веток и сообщения коммитов — только про то, ЧТО меняется в коде
оркестратора, а не про то, НАД КАКОЙ задачей ты его при этом тестировал.
Правильно: `feature/validator-in-constraints-pick`. Неправильно:
`feature/example-problem-validator-fix` (здесь `example-problem` стоит на
месте реального `problem_id` — так делать нельзя).

Если для PR description нужен пример поведения — используй синтетический
пример (`problem_id: example-problem`, произвольные `N`/условие), а не
реальный спек, даже если реальный уже лежит в `problems/<id>/` локально и
"было бы проще показать на нём".

Это ограничение — только на то, что попадает в git/PR. В обычном ответе в
терминале (не коммитящемся никуда) упоминать `problem_id` и детали спека
можно и нужно — иначе с тобой невозможно обсуждать прогон конкретной
задачи.

### Дополнительно: самопроверка перед открытием PR

Правило выше (запрет problem_id/деталей спека в git-артефактах) уже
нарушалось на практике, несмотря на то что оно явно сформулировано.
Поэтому перед `gh pr create` — обязательный дополнительный шаг:

1. Перечитать финальный текст заголовка и описания PR целиком (не
   доверять тому, что "я и так помню, что там ничего лишнего").
2. Явно проверить: нет ли упоминания того, что изменение
   тестировалось/проверялось на конкретной реальной задаче — даже без
   названия. Формулировки вида "протестировано на реальной задаче про..."
   или "проверил на примере с ограничением N ≤ 10^6 и ответом по модулю
   простого числа" — тоже запрещены, даже если problem_id нигде не назван:
   деталь задачи узнаваема сама по себе.
3. Если в PR вообще есть смысл упомянуть, что проводилась ручная
   верификация — писать только "вручную проверено на синтетическом
   примере (`example-problem`)", без каких-либо характеристик реальной
   задачи, даже отдалённых.

Если это правило нарушено снова — сообщить пользователю об этом прямо в
следующем ответе, а не полагаться на то, что он сам заметит при ревью PR.

## Ручные прогоны с реальным API — запрещены без явной команды

`orchestrator <problem_id> llm generate` (с `--step`, `--force` или без) вызывает
реальную модель и стоит каждый раз: через `AnthropicClient.generate` — денег
с API-баланса, через `ClaudeCodeClient.generate` (`claude -p`) — лимитов
подписки автора, общих с его интерактивной работой. Это не "проверка кода"
в обычном смысле — здесь любая проверка = потраченные токены.

СТРОГО ЗАПРЕЩЕНО Claude Code самостоятельно, без явной команды пользователя
в текущем сообщении, запускать:
- `orchestrator <problem_id> llm generate ...` на любом `problem_id` (реальном или синтетическом);
- любой другой код, который инстанцирует `AnthropicClient` и реально
  доходит до `client.messages.create` — включая "быстро проверить одним
  шагом", "smoke test", "прогоним и посмотрим, что вернётся";
- `claude -p` с запросом к модели (вручную или через `ClaudeCodeClient`) —
  по тем же причинам; `claude --version`/`--help` модель не вызывают и
  разрешены.

Это касается даже ситуаций, где мотивация выглядит разумной ("хочу
убедиться, что фикс действительно работает end-to-end") — инициатива здесь
неуместна: стоимость реального вызова не оправдывает прогон без спроса.

Разрешено без спроса (к модели не обращается):
- `orchestrator <problem_id> llm status` — читает только кэш и файлы, в сеть не ходит;
- `orchestrator <problem_id> llm accept` — пишет только `problems/<id>/.cache/`, к модели
  не обращается (но меняет кэш автора — запускать по его просьбе);
- `pytest` (integration-тесты по умолчанию выключены `-m 'not integration'`
  — не трогать `pyproject.toml`, чтобы это не включить случайно);
- компиляция и статический анализ сгенерированных C++-файлов;
- unit-тесты с моком `LLMClient` (Protocol в `orchestrator/llm_client.py`)
  или с замоканным `subprocess.run` для `ClaudeCodeClient`.

Если для отладки бага нужен реальный end-to-end прогон — Claude Code должен
явно спросить и дождаться отдельного подтверждения от пользователя в чате
("запускай", "прогони N" и т.п.). Формулировка вопроса сама по себе не
считается разрешением — нужен явный ответ на неё в отдельном сообщении.
