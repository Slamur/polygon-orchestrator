# Формат входного спека задачи

Формат — YAML. Один файл на задачу, лежит в её каталоге:
`outputs/<problem_id>/spec.yaml`.

Главный принцип: **всё, что требует придумывания асимптотики или матана, — поле,
которое обязан заполнить автор**. Модель работает только с тем, что явно
написано в спеке, и никогда не выводит сложность решения из текста легенды
сама. Если нужное поле пусто — соответствующий шаг оркестратора должен упасть
с ошибкой "не хватает входных данных", а не догадываться.

Черновик со всеми полями (пустыми, с подсказками в комментариях) создаёт
`orchestrator <problem_id> init` — в `outputs/<problem_id>/spec.yaml`, из
шаблона `templates/common/spec_template.yaml`. Шаблон перечисляет все поля
формата — это проверяет `tests/test_spec_init.py`, поэтому при правке
формата шаблон нужно править вместе с ним.

Ниже — поля по секциям. Отмечено `[required]` / `[optional]` для MVP
(генеративная часть без судящего контура).

```yaml
problem_id: unique-slug            # [required] латиница, совпадает с именем каталога задачи
title:
  ru: "Название на русском"        # [required] начальное название на Polygon; дальше источник — outputs/<id>/statement/name.txt
  en: "English title"              # [optional]
references:                        # [optional] общие референсы — образцы для ВСЕХ шагов, см. "Референсы" ниже
  - "templates/examples/array--prefix-sums"

# ---------------------------------------------------------------------------
# 1. ЧЕРНОВИК УСЛОВИЯ — вход для шага statement_draft
# ---------------------------------------------------------------------------
# Формат ввода-вывода отсюда передаётся и в следующие шаги:
# formal_input_sketch, indexing и input примеров — в constraints_pick
# (порядок чтения для валидатора) и generators_and_script; всё это плюс
# formal_output_sketch, output примеров и legend_sketch — в solutions_draft.
statement_draft:
  legend_sketch: |                 # [required]
    Свободный текст автора: сюжет, идея, что происходит в задаче.
    Модель НЕ обязана из этого текста выводить формальную модель —
    формальная модель дальше, отдельным полем.
  formal_input_sketch: |           # [required]
    Черновое, но по возможности формальное описание входных данных:
    что дано, в каком порядке, какие структуры (массив/дерево/граф/строка).
    Не про ограничения на числа (это ниже, в constraints) — про форму данных.
  formal_output_sketch: |          # [required]
    Аналогично — что и в каком формате нужно вывести. Явно указать,
    гарантируется ли существование/единственность ответа, или нужен
    отдельный вывод "-1"/"NO" и т.п.
  indexing: "1-indexed"            # [required] "0-indexed" | "1-indexed" | "irrelevant"
  sample_examples:                 # [required], минимум 1
    - input: |
        ...
      output: |                    # [optional]
        ...
        # Если не заполнено — автор считает точное значение неважным для
        # формулировки задачи; поле используется как подсказка при
        # написании примечания (note_hint) и как образец формата вывода для
        # solutions_draft, но в тесты Polygon не транслируется. input
        # обязателен: он переносится в реальные тесты Polygon.
      note_hint: "Что должно быть объяснено в пояснении к примеру (не сам текст)"
  known_ambiguities:               # [optional]
    - "Например: не решено, считать ли минуту точкой или отрезком времени"
  preserve_legend_verbatim: false   # [optional] bool, default: false.
    # false (по умолчанию) — стандартное правило: вводный художественный
    # абзац сокращается до 2-3 строк, а описание модели задачи (процесс,
    # правила, определения, вопрос) остаётся в легенде полностью; в формат
    # ввода/вывода переносится только описание данных (см. tutorials/statement.md).
    # true — для задач, где сама легенда содержательна и опирается на
    # реальные факты/историю, а не просто оборачивает формальную
    # постановку: модель обязана сохранять фактическую плотность
    # `legend_sketch` практически как есть. Разрешена лёгкая
    # стилистическая правка (согласование времён, связки между
    # предложениями), но не сокращение/пересказ фактов и не удаление
    # деталей. Модель не решает сама, "тривиа ли это" — только явный
    # флаг автора включает этот режим.
  references: []                     # [optional] референсы только для statement_draft (см. "Референсы")

# ---------------------------------------------------------------------------
# 2. ОГРАНИЧЕНИЯ — вход для шага constraints_pick
# ---------------------------------------------------------------------------
constraints:
  intended_complexity: "O(N log N)"   # [required] — задаётся автором, модель не выводит сама
  complexity_reasoning: |             # [required]
    Краткое обоснование автора, почему такая асимптотика (какой алгоритм
    имеется в виду). Нужно, чтобы модель могла проверить согласованность
    выбранных N/TL с этим обоснованием, а не гадать заново.
  variables:                         # [required]
    - name: "N"
      min: 1
      max: null                      # если null — модель предлагает варианты и ЯВНО помечает как "предложено"
      description: "количество вершин"
    - name: "K"
      min: 1
      max: "2*N"                     # допускается выражение через другие переменные
      description: "количество рёбер"
  special_guarantees:                # [optional] всё, что не сводится к min/max одной переменной
    - "граф связный по определению"
    - "все S_i состоят только из латинских строчных символов"
  test_groups_hint:                  # [optional] — если у автора уже есть идея по группам
    - name: "small"
      subset_of: null
      max_n: 10
    - name: "n is prime"
      subset_of: "full"
      special_property: "prime"
  test_groups_needed: false          # [optional] bool, default false — явный запрос от автора на
    # структуру тестовых групп. Если false и test_groups_hint не задан — шаг
    # constraints_pick не предлагает группы вообще. Если задан
    # test_groups_hint (непустой) — группы формируются по нему независимо
    # от значения этого флага (хинт сам по себе уже явный запрос). Если
    # test_groups_needed: true, а test_groups_hint не задан — шаг предлагает
    # разумный набор сам, как proposed (текущее поведение).
  time_limit_seconds: null           # [optional] если null — модель предлагает, помечая как black-box предложение
  memory_limit_mb: 256               # [optional], желательно кратно 256 (см. tutorials/limits.md)
  uncertain_points:                  # [optional] то, в чём сам автор не уверен — акцент для шага
    - "не уверен, что 10^6 для группы 3 — не слишком щедро для проверки TL без оптимизаций ввода"
  references: []                     # [optional] референсы только для constraints_pick (см. "Референсы")

# ---------------------------------------------------------------------------
# 3. ГЕНЕРАТОРЫ / FREEMARKER — вход для шага generators_and_script
# ---------------------------------------------------------------------------
# Форма входных данных для генераторов берётся автоматически из
# statement_draft.formal_input_sketch — отдельно в generation: её указывать
# не нужно и нельзя (лишнее поле, extra="forbid").
generation:
  generator_ideas:                   # [optional] — если автор уже придумал, какие генераторы нужны
    - name: "gen_rand"
      params: ["n", "minA", "maxA"]
      purpose: "равномерный случайный массив"
    - name: "gen_prime"
      params: ["minN", "maxN"]
      purpose: "N — простое число из диапазона"
  specific_test_ideas:               # [optional] — КОНКРЕТНЫЕ тестовые сценарии, а не генераторы
    - "N = 1 (минимальный случай)"
    - "N = N_max, значения максимальные"
    - "все элементы массива равны"
    # Это не то же самое, что generator_ideas (какой инструмент нужен) и не
    # то же самое, что solutions.known_wrong_approaches (что ломает
    # конкретное неверное решение) — это отдельный список "что обязательно
    # должно быть протестировано", который автор формулирует сам, не
    # выводя его из легенды/асимптотики.
  script_style: "groups"             # [required] "flat" | "groups" — простой скрипт (test_script) или по группам тестов (test_script_groups)
  references:                        # [optional] референсы только для шага generators_and_script, добавляются к общим
    - "outputs/old-task"
    - "my_examples/gen_tree.cpp"

# ---------------------------------------------------------------------------
# 4. АВТОРСКИЕ РЕШЕНИЯ (опционально, черновики) — вход для шага solutions_draft
# ---------------------------------------------------------------------------
solutions:
  wanted_verdicts: ["ok", "wa", "tl"]  # [required если секция включена] какие черновики нужны: ok, wa, tl, tl_ok, ml, re
  languages: ["cpp", "java"]           # [required если секция включена]
  algorithm_hint: |                    # [required если секция включена]
    Автор явно описывает идею основного алгоритма (не полный код, но
    достаточно, чтобы не пришлось заново выводить асимптотику).
  alternative_approaches:              # [optional] — другие верные идеи, по ok-решению на каждую
    - "двоичный поиск по ответу вместо двух указателей"
    # Без префикса языков — решение на каждом языке из `languages`, где
    # идея применима; префикс "(<языки через />): " сужает набор.
  known_wrong_approaches:              # [optional] — идеи для wa/tl/tl_ok-решений
    - "wa: off-by-one в правой границе диапазона"
    - "tl (cpp/java): O(N^2) перебор без оптимизации"
    - "tl_ok: верный алгоритм с небуферизованным вводом-выводом"
    # Каждый пункт — отдельное решение solutions_draft, пункты не
    # пропускаются и не заменяются другими; один пункт — одна ошибка (две
    # независимые ошибки — два пункта). Необязательный префикс
    # "<вердикт> (<языки через />): " задаёт вердикт и языки решения
    # (`tl_ok` — "TL или OK": пограничное по времени решение или решение
    # без ускорения ввода-вывода). Без языков они выбираются по вердикту:
    # tl — C++; tl_ok — все языки из `languages`, где это имеет смысл;
    # wa из-за переполнения — один из C++/Java; прочие wa — один язык, где
    # ошибка естественнее. Если для вердикта из wanted_verdicts нет ни
    # одного пункта, модель предлагает один подход сама (как proposed);
    # сочетания "вердикт × язык" не дополняются. Исключение — slowio: при
    # вводе или выводе порядка 10^5 значений и больше модель сама добавляет
    # "tl_ok"-решение с медленным вводом-выводом на Java и Python из
    # languages, если такого пункта для языка нет (как proposed).
  references: []                       # [optional] референсы только для solutions_draft (см. "Референсы")

# ---------------------------------------------------------------------------
# СЛУЖЕБНОЕ
# ---------------------------------------------------------------------------
checker:
  standard: "ncmp"                   # [optional] имя стандартного чекера ИЛИ null
  custom_needed: false                # [required] bool
  custom_comparison_notes: null       # [required если custom_needed=true] — как сравнивать ответы,
                                       # точность для вещественных и т.д. (см. tutorials/checker.md)
  references: []                      # [optional] референсы только для checker_draft (см. "Референсы")

meta:
  requirements_docs:                  # ссылки на приложенные md с правилами — не дублируются в спеке,
    - "templates/common/tutorials/statement.md"
  status: "draft"                     # "draft" | "ready_for_generation" | "reviewed"
```

## Почему именно так

- **`intended_complexity` и `complexity_reasoning` обязательны в `constraints`.**
  Это прямая реализация твоего решения "модель не должна сама выводить
  асимптотику из текста". Если поле пустое — шаг `constraints_pick` обязан
  остановиться с явной ошибкой, а не подставить что-то правдоподобное.
- **`max: null` у переменной — это не "забыл", а явный сигнал "предложи
  варианты"**, и в этом случае ответ модели должен быть помечен как
  предложение, а не факт (см. правило эскалации в CLAUDE.md).
- **`uncertain_points` есть на двух уровнях** (автора — в спеке, и модели — в
  выводе). Это разные вещи: одно — то, в чём не уверен ты, другое — то, в чём
  агент должен признаться, что не уверен, даже если ты не спрашивал.
- **`references`** — явная привязка к образцам (см. "Референсы" ниже),
  чтобы шаги не изобретали структуру файлов заново, а расширяли то, что
  автор уже использует. Без референсов модель получает только правила
  (`templates/common/`).
- Поля вроде `time_limit_seconds` и переменные без `max` **допускают null**
  осознанно — это единственное место, где модели разрешено предлагать
  число, но обязательно с пометкой "предложено, не проверено".

## Референсы

`references` — список путей от корня репозитория на файлы или каталоги,
которые прикладываются к вызову модели как образцы. Бывают общие (в корне
спека — для всех шагов) и шаговые (в секции шага — только для него):

| Секция | Шаг |
|--------|-----|
| `statement_draft.references` | `statement_draft` |
| `constraints.references` | `constraints_pick` (и валидатор) |
| `generation.references` | `generators_and_script` |
| `solutions.references` | `solutions_draft` |
| `checker.references` | `checker_draft` |

Шаговые референсы добавляются к общим, а не заменяют их.

**Каталог-референс** устроен как `outputs/<problem_id>/` — результат
оркестратора: учебная задача `templates/examples/<problem_id>/`, прошлая
задача автора в `outputs/<problem_id>/` (в том числе выгруженная
`polygon pull`) и т.п. Каждый шаг берёт из каталога только свою
часть (`REFERENCE_DOCUMENTS` в `orchestrator/references.py`):

| Шаг | Файлы из каталога |
|-----|-------------------|
| `statement_draft` | `statement/*.tex` |
| `constraints_pick` | `constraints.yaml`, `validator.cpp` |
| `generators_and_script` | `constraints.yaml`, `generators/*.cpp`, `test_script`, `test_script_groups` |
| `solutions_draft` | `solutions/*` на языках из `solutions.languages` |
| `checker_draft` | `checker.cpp` |

Если в каталоге есть `spec.yaml` (спек той задачи, как у учебных задач), он
прикладывается вместе с ними — модель видит пару "спек → результат". Это
относится и к прошлым задачам автора в `outputs/<problem_id>/`; у задачи,
выгруженной `polygon pull` без спека, приложен будет только результат.

**Файл-референс** прикладывается как есть — общий ко всем шагам, шаговый к
своему шагу.

Ошибки референсов проверяются до вызова модели (`llm generate` останавливает
задачу, `llm status` показывает шаг как `blocked`):
- путь не существует;
- шаговый каталог-референс не дал своему шагу ни одного файла;
- общий каталог-референс не дал ни одного файла ни одному шагу.

Общий каталог, в котором нет части для какого-то шага (например, у задачи
со стандартным чекером нет `checker.cpp`), этому шагу просто ничего не даёт.

Содержимое приложенных файлов входит в хеш промпта шага: правка
референса (в том числе `outputs/<другая задача>/`) инвалидирует кэш шагов,
которые его получают.

Поле `generation.base_template_refs` из прежней версии формата удалено —
его заменяет `generation.references`.
